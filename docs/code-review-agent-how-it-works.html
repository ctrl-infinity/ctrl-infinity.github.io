How the Code Review Agent Works

One webhook covers every repository in the project. Claude Code reviews each pull request headlessly and posts back a structured, reproducible verdict — no per-repo setup, ever.

Live — shipped, running today Planned — designed, not yet shipped

Phase ATrigger

PR opened or updated LIVE

In any repository in the project — no per-repo setup, ever.

Project-wide service hook fires LIVE

Azure DevOps posts git.pullrequest.updated to one Incoming Webhook, which triggers the central pipeline — covering every current and future repo automatically, since Azure Repos has no native way to attach a policy to "all repos."

Guard against spurious triggers, then clone LIVE

The public webhook endpoint also receives service-hook test payloads and stray POSTs. The pipeline confirms the PR is real before doing any work, then dynamically clones the triggering repo — its identity is only known at runtime.

Phase BGather context

Diff the pull request LIVE

target...source, size-capped by bytes and lines — an oversized PR gets a "please split this up" note instead of a runaway run.

Pull the linked work item LIVE

Title, state, and acceptance criteria, fetched via a reusable skill — so the reviewer can judge whether the change actually does what the story asked, not just whether the code is clean.

Attach full file content PLANNED

Changed files pasted in full, not just diff hunks, so the model reasons over real surrounding code — pre-attached once, at zero extra agent turns.

Read the existing PR discussion PLANNED

Prior human comments and the bot's own last review, so it stops repeating itself — instead reporting each earlier finding as fixed, still open, or unclear.

Check repo conventions & config PLANNED

CLAUDE.md and lint config, read once with no agent turns spent finding them — plus a per-repo .code-review.yml a team can drop in to tune caps, severity floor, or opt out entirely.

Phase CReview

Claude runs the code-reviewer subagent LIVE

One version-controlled ruleset drives both CI and local reviews. Tool access is read-only and scoped — Read, Grep, Glob, git-only Bash — no writes, no commits, no pushes.

Findings come back as strict JSON LIVE

Severity, category, verdict, one entry per finding — no prose, no markdown fences, so the same output renders the same way every run. See the contract below.

Phase DPublish

One sticky summary comment LIVE

A hidden marker lets the pipeline find its own last comment and update it in place — every push refreshes the same thread instead of spawning a new one.

Inline, line-anchored threads PLANNED

Each finding attaches directly to its changed lines. A fingerprint per finding lets re-runs update or skip instead of duplicating.

Resolve-on-fix PLANNED

A thread the agent raised auto-resolves once the line it flagged is gone — never reopened over a human's dismissal.
